指定された Issue を1件実装する。指定がない場合は、`status: created` で依存関係が満たされた Issue のうち番号の最も小さいものを選び、着手前にユーザーに伝える。

## 原則

- **根拠は正の文書だけ**：実装の根拠は Issue と、Issue が参照する ID の定義（`spec/`、`docs/D1/`、`docs/D2/`）とする。`docs/work/` の記録を根拠にしない。
- **範囲を広げない**：Scope にないことは実装しない。必要だと気づいた作業は、新しい Issue の候補として記録する。
- **テストを都合よく変えない**：既存のテストを、通すためだけに書き換えたり削除したりしない。Issue が仕様の変更を求めている場合に限り、その変更に合わせて更新する。
- **一次ドキュメントは承認なしに変えない**：変更が必要な場合は、上流への反映に「承認待ち」と書き、ユーザーに確認する。

## 手順

### 1. 着手

1. Issue を読み、Dependencies の Issue が `done` であることを確認する。満たしていなければ着手せず、ユーザーに伝える。
2. `requires: human` の場合は、Implementation notes のうち人が行う作業を一覧にしてユーザーに示し、エージェントが行う部分だけを進める。人の作業が終わるまで `done` にしない。
3. ブランチ `issue/NNN-<内容>` を作り、フロントマターを `status: doing` にする。
4. Issue が参照する ID（`plan`、`requirements`、`ui`）の定義を、正の文書で読む。変更 Issue の実装の場合は、依存するドキュメント Issue の差分と影響範囲も読む。

### 2. 実装（TDD）

`../implementation-planning/references/tdd.md`（このスキルのディレクトリからの相対パス）に従い、Tests の項目を1件ずつ red → green で進める。

- テスト名の先頭に、検証する要件 ID を書く（例：`FR-T-7: 返信があるスレッドは削除できない`）。
- 型名、テーブル名、変数名、画面の文言は、`docs/D2/GLOSSARY.md` の「コード上の名前」と「用語」に合わせる。用語集にない概念が必要になった場合は、3 の扱いに従って先に用語集に追加する。
- 画面を追加・変更した場合は、`docs/D2/UI_GUIDELINES.md` のセルフチェックを行い、記録を `docs/work/design/` に残す。

### 3. 実装中に決めたこと

文書に書かれていない判断が必要になった場合は、次のように扱う。

| 判断の種類 | 扱い |
|---|---|
| 実装の詳細（文書の記述に影響しない） | Issue の末尾に「実装メモ」として記録する |
| 正の文書（`docs/D1/`、`docs/D2/`）の記述に影響する | 該当する文書を更新し、Issue に「上流への反映」節を設けて記録する。ID の規則に従う |
| 一次ドキュメント（`spec/`）に影響する | 作業を止めてユーザーに確認する。承認されるまで「承認待ち」とする |

### 4. 検証

次をすべて実行し、結果を確認する。コマンドは `AGENTS.md`（または `CLAUDE.md`）のコマンド欄に従う。

- テスト、型チェック、（定められていれば）カバレッジ
- ID の機械検査：`python3 ../spec-analyze/scripts/trace_check.py --root .`（このスキルのディレクトリからの相対パス）。今回追加・変更した ID とテストについて、ERROR と WARN がないこと
- 変更 Issue の場合：skill `spec-analyze` を `change` の段階で実行し、CRITICAL と HIGH の指摘がないこと

### 5. レビュー

完了とする前に、新しい文脈のサブエージェント（使えない環境では別のセッション）に差分をレビューさせる。作業した文脈のままでは、同じ前提で見落とすため。

- レビュアーに渡すもの：差分（`git diff main...HEAD`）、Issue、Issue が参照する ID の定義。実装の経緯は渡さない。
- 確認させること：受け入れ条件と参照する要件がすべて満たされているか、要件 ID ごとにテストがあるか、Scope 外の変更がないか、上流への反映の漏れがないか。
- 報告させるもの：正しさと要件に関わる問題だけ。好みや、起こり得ないケースへの防御は報告させない。指摘を探す役割を与えると、問題のない箇所にも指摘を作りがちなため。
- 結果は `docs/work/reviews/YYYY-MM-DD-issue-NNN.md` に保存する。
- 受け入れ条件や要件に関わる指摘は、この Issue の中で直す。それ以外で対応が必要なものは、skill `create-local-issue` で新しい Issue にする（その場合は Issue 番号をレビュー記録に書く）。

### 6. 完了

1. 受け入れ条件のチェックボックスを、根拠（テスト名、コマンドの結果、セルフチェックの記録）を確認したうえでチェックする。
2. Issue の末尾に「実装メモ」として、主な判断、作成したテスト、レビュー記録のパスを書く。
3. 変更 Issue の場合は、上流への反映がすべて「反映済み」または「不要」であることを確認する。
4. `status: done` にしてコミットする。コミットメッセージに Issue 番号を含める。
5. マージの方法はプロジェクトの規則（`AGENTS.md`）に従う。規則がなければユーザーに確認する。
6. ユーザーに、実施内容、検証の結果、レビューの指摘と対応、新しく作った Issue を報告する。

## 止める場合

次の場合は作業を止め、`status: stop` にして理由を Issue に書き、ユーザーに伝える。

- 受け入れ条件が文書と矛盾していて、どちらに合わせるか判断できない
- 一次ドキュメントの変更が必要で、承認が得られていない
- 同じ失敗の修正を繰り返しても解決せず、前提の見直しが必要
